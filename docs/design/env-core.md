# Environment config core

Status: **implemented**. Operator steps: [DEVELOPMENT.md](../DEVELOPMENT.md) → Production. Adding a variable: [EXTENDING.md](../EXTENDING.md) → Environment variables. Adapted from the boilerplate's env core; Rentopya keeps its own `prod-env.sh` command line (`init -o FILE --app-url URL`, `upgrade FILE`, `check FILE`), which the CI `prod-env` job, `make prod-env*` and `scripts/server-sync.sh` use.

## 1. Goal

One versioned schema is the source of truth for the production env. Everything else is generated from it or checked against it in CI:

| Surface | Role | Kept in line by |
|---|---|---|
| `deploy/env/schema` | Production keys, how each value is made, `@version` | — (source) |
| `.env.server` (on the host / in Dokploy) | The real production env | `scripts/prod-env.sh init / upgrade / check` |
| `.env.server.example` | Committed key list for operators | generated: `scripts/prod-env.sh example`; CI diffs it |
| `.env.example` | Local development defaults (hand-written) | CI: every schema key and every `compose.prod.yml` variable has a line |
| `compose.prod.yml` `x-backend-environment` | What reaches the backend / worker containers | CI: every backend env read is delivered or has a decision in `deploy/env/compose-env.allow` |
| `backend/internal/config` | What the backend reads; boot-time guard | Go tests: every schema secret the backend reads is guarded |

Local development needs no generator: `cp .env.example .env && make local-dev`.

## 2. Schema format

`deploy/env/schema`, one managed key per line (`KEY | rule`):

| Rule | Meaning |
|---|---|
| `ask:APP_URL` | The only question `init` asks (or `--app-url`). |
| `derive:<template>` | Computed: `{APP_HOST}` (host of `APP_URL`) and `{KEY}` of any earlier key. |
| `const:<value>` | Fixed default. |
| `secret:hex\|b64\|alnum:<n>` | Generated by openssl once (`hex`/`b64`: n bytes, `alnum`: n chars), kept forever. |
| `vapid:public` / `vapid:private` | Web Push P-256 key pair (base64url), generated together. |
| `empty` | Managed but blank; the operator fills it (SMTP, Sentry, Dokploy API, backups, mobile auth). |

Directives: `@version N` (bump on every change; stamped as `ENV_SCHEMA_VERSION`), `@rename OLD NEW N` (upgrade moves the value), `@remove KEY N` (upgrade comments it out).

Comments: `##` lines are schema-only notes. `# --- Title ---` starts a section. Any other `#` line is an operator note and is copied into `.env.server` and `.env.server.example` under its section.

What belongs in the schema: every key `compose.prod.yml` requires, every secret, every URL derived from the app URL, and the optional keys operators actually set (mail, Sentry, provider endpoints, production-guard switches, alerts, WhatsApp gateway, custom site domains, backups, mobile auth, Expo push). Tunables with a safe Go default (`LOG_FORMAT`, `QUEUE_CONCURRENCY`, `TENANCY_CACHE_TTL`, timeouts, TTLs, …) stay out; they keep their `compose.prod.yml` default and are documented in `.env.example`.

What never belongs in env: provider credentials. iyzico merchant keys, Netgsm accounts, the e-invoice integrator, KABİS, HGS, Yolcu360 / Obilet and the WhatsApp sessions are per organization, sealed with `APP_ENCRYPTION_KEY` in the integration vault (`integration-adapter` skill). The env only carries platform-level endpoints (`IYZICO_*_BASE_URL`, `NETGSM_*_BASE_URL`), the wuzapi gateway's own admin token / encryption key, and the `*_ALLOW_PRODUCTION_IN_NON_PROD` switches.

## 3. `scripts/prod-env.sh`

bash 4+, openssl, awk; no network. Tests: `scripts/prod-env.test.sh`.

- **`init [-o FILE] [--app-url URL]`** writes a fresh file (mode 600): derives every URL, generates every secret and the VAPID pair. Refuses to overwrite.
- **`upgrade FILE [-o OUT]`** brings a file to the current `@version`: keeps every existing value, applies `@rename` / `@remove`, generates only keys that are missing (or blank secrets / URLs), keeps unknown keys under "Unmanaged", backs up to `FILE.bak.<timestamp>`.
- **`check FILE`** exits 1 on a missing key, a blank secret or URL, a secret still holding its public `.env.example` value, or a schema version gap. `scripts/server-sync.sh` runs `upgrade` when `check` fails.
- **`example`** prints `.env.server.example`: every key with its notes, non-secret values for `https://app.example.com`, secrets blank with a `# secret: generated by init (…)` note. Deterministic, so CI can diff it. Never edit the file by hand.

Secret safety: `upgrade` never regenerates an existing secret. To replace a leaked or development secret, delete its line and run `upgrade`. What a new value breaks: `JWT_*` / `AUTH_SECRET` sign everyone out, `CENTRIFUGO_*` drops realtime connections, the VAPID pair drops every push subscription, `REDIS_PASSWORD` / `S3_*` / `MEILI_MASTER_KEY` must match the restarted services, `DB_PASSWORD` needs `ALTER USER` first (Postgres keeps it in its volume), `WUZAPI_ENCRYPTION_KEY` unlinks every WhatsApp session. **Never** replace `APP_ENCRYPTION_KEY` on an install with data: integration credentials, OAuth secrets and encrypted personal data become unreadable. `.env.server.*` (backups included) is git-ignored; the script prints key names, never values.

## 4. CI checks (`make env-check`, CI job `env`)

`scripts/check-env-sync.sh`:

1. `.env.server.example` equals `scripts/prod-env.sh example` (fix: `scripts/prod-env.sh example > .env.server.example`);
2. every schema key has a local default in `.env.example`;
3. every `${VAR}` that `compose.prod.yml` interpolates is a schema key or documented in `.env.example`;
4. `scripts/prod-env.test.sh` passes.

`scripts/check-compose-env.sh` (+ `scripts/check-compose-env.test.sh`): every env var the Go backend reads must reach the `backend` and `worker` containers or carry a decision in `deploy/env/compose-env.allow`.

- Read set: string-literal `getEnv` / `getInt` / `getInt64` / `getBool` / `getDuration` / `getFloat` / `os.Getenv` / `os.LookupEnv` calls in non-test Go files under `backend/`. Keep reads literal: the production-guard keys are read as literals in `config.go` for this reason (a test keeps them equal to the `envguard` constants).
- Delivered set: each service's environment from `docker compose config`, resolved with an env generated from the schema, so anchors and overrides count, and a compose variable the schema does not manage fails the check.
- Allowlist lines are `KEY | omit|wire | reason`. `omit`: deliberately not delivered (storage aliases, `REDIS_DB`, `SMTP_FROM`, `CENTRIFUGO_ENABLED`). `wire`: should be delivered, reported as a warning with a `KEY: ${KEY:-}` snippet (an empty value keeps the Go default). Stale entries fail.

The CI `prod-env` job stays: `init` → `docker compose … config -q` → `check` proves a schema-generated env is enough for `compose.prod.yml`.

## 5. Runtime guard (`backend/internal/config/guard.go`)

Called from `Config.validate()` at boot of the API, the worker and every command that loads the config.

1. **`APP_ENV`** (normalized by `envguard.Normalize`: trimmed, lower-cased, empty = `development`) must be `development`, `staging`, `production` or `test`. Anything else stops the process, with a hint for common slips (`prod` → `production`, `dev` → `development`).
2. **`managedSecrets`**: one row per backend secret (`DB_PASSWORD`, `REDIS_PASSWORD`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `AUTH_ADAPTER_SECRET`, `APP_ENCRYPTION_KEY`, `CENTRIFUGO_API_KEY`, `CENTRIFUGO_TOKEN_HMAC_SECRET`, `MEILI_MASTER_KEY`, `WUZAPI_ADMIN_TOKEN`) with its public development values and when it applies (Centrifugo enabled, search enabled, an S3 storage driver, the wuzapi gateway configured). Outside `development` / `test` (staging included) an empty or development value is refused and every offender is listed in one error. `JWT_ACCESS_SECRET` must also be at least 32 characters.
3. **Schema link** (`guard_test.go`, reads `deploy/env/schema` and `.env.example` from the checkout): every `secret:` / `vapid:` key has a row or an entry in `unguardedSchemaSecrets` with a reason (`AUTH_SECRET`, `SITE_EMBED_SECRET`: frontend / site only; `WUZAPI_ENCRYPTION_KEY`: wuzapi only; the VAPID pair); every non-empty `.env.example` value of a guarded key is in its row's defaults; each row reads the env key it names through the real `Load()`.

The provider rules of `internal/platform/envguard` (fake providers outside production only, official KABİS / e-invoice / Netgsm endpoints refused outside production unless `*_ALLOW_PRODUCTION_IN_NON_PROD`) are unchanged and documented in `docs/operations/observability.md`.

## 6. Not covered

- The frontend and site containers: their `process.env.*` reads (with `NEXT_PUBLIC_*` inlined at build time) are delivered by hand in `compose.prod.yml`; there is no extractor for them yet.
- Spaceship / DNS automation has no env keys today; a platform-level DNS API key would be a schema `empty` key plus a `managedSecrets` row if the backend reads it.
- Encrypted secrets in git (SOPS / age): out of scope; Dokploy holds the env.
