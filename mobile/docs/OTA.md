# Release and OTA updates

Rentopya ships the mobile app in two ways:

- **EAS Update (OTA)** for JavaScript and asset changes. No new store build is needed.
- **Store build** when the native side changes. Android builds on EAS and goes to Play internal as a draft. iOS builds on Xcode Cloud and goes to TestFlight.

CI picks the way per platform from the native **fingerprint**. Nobody runs `eas update` or `eas build` by hand for a normal release.

## Configuration

- Runtime version policy: `fingerprint` (`app.json`). The runtime version is a hash of everything that affects the native app: native dependencies, config plugins, the resolved app config, patches and the SDK version. An update only reaches binaries built from the same native state. A JS bundle that needs a new native module therefore never lands on an older binary.
- `mobile/ios/` and `mobile/android/` are generated by prebuild (CNG) and are gitignored. The only tracked part is `mobile/ios/ci_scripts`. The hash is the same before and after `expo prebuild --clean`. Check it with `npx expo-updates fingerprint:generate --platform ios|android`.
- The app checks for updates itself when it comes to the foreground (`src/core/updates.ts`; `checkAutomatically: NEVER` in `app.json`). A downloaded update applies on the next start, or right away from the banner.
- Update URL: `app.config.js` sets `https://u.expo.dev/<projectId>` once `expo.extra.eas.projectId` is in `app.json` (`eas init`).
- Channel: `app.config.js` writes the `expo-channel-name` request header. Xcode Cloud builds are not EAS builds, so they get no channel from `eas.json`. The channel is taken from:
  1. `EXPO_UPDATES_CHANNEL`, if set;
  2. otherwise `EXPO_PUBLIC_APP_ENV`: `production` gives `production`, `preview` gives `preview`;
  3. anything else gives `development`.

  The `eas.json` profiles use the same channel names.

- Store guard: with `EXPO_PUBLIC_APP_ENV=production`, `app.config.js` refuses an `EXPO_PUBLIC_API_MODE` other than `live`. It also refuses a non-`https://` `EXPO_PUBLIC_API_URL`.

## One list of release values: `mobile/release.env`

Some values end up in the app config. When they differ between the release job, the EAS `production` environment and Xcode Cloud, the iOS binary and the OTA updates have different fingerprints. Updates then never reach that binary. These values are kept in one committed file, `mobile/release.env`:

| Key                                | Value                      | Why                                               |
| ---------------------------------- | -------------------------- | ------------------------------------------------- |
| `EXPO_PUBLIC_APP_ENV`              | `production`               | channel, store guard                              |
| `EXPO_PUBLIC_API_MODE`             | `live`                     | never a mock or demo API in a store binary or OTA |
| `EXPO_PUBLIC_APPLE_SIGN_IN`        | empty or `1`               | adds the Sign in with Apple entitlement           |
| `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` | empty or the iOS client id | adds the Google URL scheme plugin                 |

Three places read this file:

- `scripts/ci/mobile-release.sh` exports these values before it computes the iOS fingerprint. It refuses to ship unless the EAS `production` environment holds exactly the same values. An empty value here means the variable must be unset in EAS. The script also requires an `https://` `EXPO_PUBLIC_API_URL` in EAS.
- `ci_scripts/ci_post_clone.sh` (Xcode Cloud) exports these values for prebuild and the JS bundle. It stops if the Xcode Cloud workflow sets one of them to a different value. On an `ios-build-*` tag, it also stops if its fingerprint does not match the hash in the tag.
- `scripts/ci/mobile-release.test.sh` tests both checks.

To change a value, update `release.env` and the EAS `production` environment together. The change needs a new store build on both platforms, and CI starts those builds by itself.

Values that are not in the fingerprint are set in each place separately and must still match. They are `EXPO_PUBLIC_API_URL`, `EXPO_PUBLIC_WEB_URL` and `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`. Set them in the EAS `production` environment and in the Xcode Cloud workflow.

## CI release flow

`.github/workflows/ci.yml` runs a `mobile-release` job. That job calls `.github/workflows/mobile-release.yml`, which runs `scripts/ci/mobile-release.sh`. The job runs only when all of these are true:

- the event is a push to `main`. It never runs on `cc-collective-branch`, a feature branch or a PR;
- the push itself changed a shipping file under `mobile/`. `*.md` and `mobile/docs/` changes do not count;
- `backend`, `frontend` and `mobile` passed;
- the repo variable `MOBILE_RELEASE_ENABLED` is `true`.

Otherwise the job is **skipped**, and the `ci` gate treats a skipped job as passed.

Backend or OpenAPI changes never release the app by themselves. The `mobile` check job does run on every `backend/docs/openapi.yaml` change. If the committed `src/core/api/schema.d.ts` is stale, `npm run api:check` fails there. After you regenerate and commit the types, that `mobile/` diff releases the app.

Each platform is decided separately:

| Native fingerprint | Android                                                                       | iOS                                                                        |
| ------------------ | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Unchanged          | `eas update --channel production`                                             | `eas update --channel production`                                          |
| Changed            | `eas build --profile production --auto-submit`, then Play internal as a draft | pushes the tag `ios-build-<hash12>`, which starts the Xcode Cloud workflow |

- **Android:** the script compares against the last finished store build (`eas fingerprint:compare`). If there is no store build yet, it builds.
- **iOS:** the script looks for an `ios-build-<hash12>` tag on `origin`. If no tag exists, it pushes one. An `ios-build-*` tag means a build was **started**, not that it succeeded. After a failed Xcode Cloud build, run the workflow by hand with `force_build`. That pushes `ios-build-<hash12>-2`, then `-3`, and so on.
- If the script cannot make a decision (`eas` errors, no fingerprint), it stops. It never falls back to an OTA.
- Manual run: Actions → **Mobile release** → _Run workflow_, with the inputs `platform` (`all`, `ios` or `android`), `force_build` and `dry_run`. `dry_run` is **on** by default. A dry run prints the decision and publishes nothing, with no update, build or tag. Only a dry run may start from a branch other than `main`.
- Local check of the script, with fake `eas`, fingerprint and git remote: `scripts/ci/mobile-release.test.sh`. It also runs in the `mobile` CI job.

1. **EAS project.** In `mobile/`, run `npx eas-cli@latest init`. It writes `expo.extra.eas.projectId` into `app.json`; commit it. The release script refuses to run without it. `app.config.js` derives the update URL from it.

   - `EXPO_PUBLIC_APP_ENV=production`
   - `EXPO_PUBLIC_API_MODE=live`
   - `EXPO_PUBLIC_API_URL=https://<api host>`
   - `EXPO_PUBLIC_WEB_URL=https://<panel host>`

## Rollback

Use the EAS dashboard: open the project, go to Updates, choose the `production` channel, then roll back or republish the last good update.

Alternatively, from the CLI (owner):

```sh
eas update:republish --channel production --group <known-good-update-group-id>
eas update:rollback <bad-update-group-id> --message "Rollback"
```

## When a new native build is required

Any change to native code or native configuration needs a new build. Examples:

- adding, removing or upgrading native modules;
- the Expo SDK, React Native or config plugins;
- permissions, entitlements or URL schemes (`release.env`);
- icons, splash, Info.plist or AndroidManifest values.
- the iOS widget list and sizes (`expo-widgets` in `app.json`), the App Intents and Siri phrases (`app-intents/`, `plugins/app-shortcuts/`). A layout change in `src/widgets/*.tsx` alone is JavaScript and ships as an OTA.

With the `fingerprint` policy, these changes produce a new runtime version. CI then builds instead of publishing an OTA. You do not need to bump `expo.version` for this.
